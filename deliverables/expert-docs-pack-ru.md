# Пакет документации для экспертов (MVP)

Дата: 2026-02-24  
Назначение: материал для QR с документацией на предзащиту/защиту.

## 01. Описание формата и структуры входных данных

### 1) Вход в систему
- Источник ввода: ручной текст и/или файл.
- API: `POST /api/case/parse`.
- Поддерживаемые форматы: `pdf`, `doc`, `docx`, `txt`, `md`, `csv`, `tsv`, `json`, `rtf`, `xml`, `html`, `yaml`, `yml`, `log`, `ini`, а также best-effort для прочих бинарных форматов.

### 2) Канонический формат `CaseInput`
- `diagnosis: string` (обязательно)
- `stage: string`
- `sex: male | female | other | unknown`
- `age: number | null`
- `histology: string`
- `biomarkers: string[]`
- `comorbidities: string[]`
- `prior_surgeries: string[]`
- `radiation_history: string[]`
- `labs: Record<string, string>`
- `contraindications: string[]`
- `timeline: { event_date, event_type, payload }[]`
- `current_plan: string[]`
- `as_of_date: string` (обязательно; ключ для ретроспективной проверки)

### 3) Источники базы знаний
- Минздрав РФ (основной российский источник).
- Дополнительные источники source-catalog: RUSSCO, NCCN (patients/professional), ESMO, ASCO, PubMed, FEMB.

### 4) Требования к данным
- Только обезличенные кейсы.
- Корректный `as_of_date` обязателен для исторически корректного выбора версии КР.
- Для сканированных PDF без текстового слоя требуется OCR (Post-MVP).

## 02. Инструкция по загрузке и вводу истории болезни

### 1) Базовый сценарий в интерфейсе `/doctor`
1. Открыть страницу `/doctor`.
2. Загрузить файл или вставить текст.
3. Нажать `Разобрать вход и автозаполнить кейс`.
4. Проверить автозаполненные поля (диагноз, стадия, биомаркеры, текущий план, дата проверки).
5. Настроить источники (чекбоксы + policy по каждому источнику).
6. Выбрать `retrieval_mode` (`auto` по умолчанию).
7. Запустить `Проверить кейс`.

### 2) Рекомендуемые настройки MVP
- `source_selection`: минимум `minzdrav`.
- `source_policy`:
  - `minzdrav = LOCAL_ONLY`,
  - остальные источники `LOCAL_THEN_ONLINE` при необходимости.
- `retrieval_mode = auto`.
- `online_fallback = true`.

### 3) Контроль качества перед отправкой результата
- Проверить, что заполнен `as_of_date`.
- Убедиться, что в `current_plan` нет пустых/дублирующих пунктов.
- Проверить наличие `evidence` и `applied_guideline_versions` в ответе.

## 03. Описание логики работы системы

### 1) Модель преобразования
- `Input`: обезличенный клинический кейс.
- `Process`: парсинг -> нормализация -> выбор релевантных КР по дате -> retrieval -> rule-based валидация -> (опционально) LLM-слой.
- `Output`: статус соответствия, список несоответствий/конфликтов, доказательная база, метрики уверенности и трассируемости.

### 2) Ключевая бизнес-логика MVP
- Ретроспективный выбор КР (`publish_date <= as_of_date`), при отсутствии точного попадания берется ближайшая доступная версия.
- Для каждого пункта плана лечения выполняется retrieval релевантных фрагментов.
- Детерминированная проверка формирует:
  - `matches`,
  - `mismatches`,
  - `missing_actions`,
  - `conflicts`.

### 3) LLM-слой
- Врачебный режим: формирует RAG+KAG заключение с цитатами.
- Пациентский режим: формирует понятное объяснение и вопросы к врачу.
- При отсутствии `OPENAI_API_KEY` врачебный API возвращает `rules-only`.

## 04. Формат выдачи результата и принципы интерпретации

### 1) Структура результата валидации врача
- `status`: `compliant | review_required`
- `matches`: подтвержденные элементы плана
- `mismatches`: пункты плана без подтверждения
- `missing_actions`: вероятно пропущенные действия
- `conflicts`: потенциально опасные пункты
- `evidence`: найденные фрагменты рекомендаций
- `applied_guideline_versions`: версии КР, на которые опиралась проверка
- `source_traceability_rate`: доля прослеживаемости решения
- `source_coverage`: покрытие по источникам
- `retrieval_mode_used`, `confidence`, `warnings`, `latency_ms`, `generated_at`

### 2) Принципы интерпретации
- `compliant` не означает клинический приказ: это признак отсутствия обнаруженных несоответствий в текущем корпусе знаний.
- `review_required` означает необходимость ручной проверки врачом.
- Наличие `warnings` и низкой `confidence` требует повышенной осторожности.
- Любой вывод должен подтверждаться `evidence` и ссылками на первоисточники.

## 05. Ограничения, допущения и область применимости

### 1) Ограничения MVP
- Система не назначает лечение и не заменяет врача.
- Нет прямой интеграции с МИС/EMR.
- Для сканов без текстового слоя OCR не входит в текущий MVP.
- Покрытие международных источников неравномерно (часть работает в online-only режиме).

### 2) Допущения
- Кейс обезличен и содержит достаточный объем клинических данных.
- Дата `as_of_date` соответствует периоду принятия клинического решения.
- Используемые источники доступны на момент синхронизации/запроса.

### 3) Область применимости
- Ретроспективный аудит и учебно-экспертные сценарии.
- Поддержка принятия решений, но не автономная клиническая система назначения.

## 06. Методология валидации и метрики качества

### 1) Наборы сценариев
- `retrospective`: исторические клинические ситуации.
- `synthetic`: контролируемые сценарии с заранее известным ожидаемым исходом.
- `literature`: сценарии на основе литературных кейсов.

### 2) Метрики
- `protocol_match_accuracy` = доля совпадений ожидаемого и фактического статуса.
- `mismatch_detection_precision` = точность обнаружения несоответствий.
- `mismatch_detection_recall` = полнота обнаружения несоответствий.
- `median_validation_time` = медиана времени валидации.
- `case_coverage` = доля кейсов с найденными доказательствами.
- `source_traceability_rate` = средняя прослеживаемость по источникам.

### 3) Текущий снимок MVP (по отчету от 2026-02-20)
- `scenarios_total`: 5
- `protocol_match_accuracy`: 0.60
- `mismatch_detection_precision`: 0.50
- `mismatch_detection_recall`: 1.00
- `median_validation_time`: 270 ms
- `case_coverage`: 1.00
- `source_traceability_rate`: 1.00

### 4) Комментарий к метрикам
- Метрики предназначены для итераций MVP и не являются клиническими claims.

## 08. Архитектура решения

### 1) Контур приложения
- Frontend: страницы `/doctor`, `/patient`, `/benchmark`, `/sources`.
- Backend API: route handlers (`/api/*`).
- Data layer: SQLite + FTS5.
- AI layer: rule engine + retrieval + OpenAI (опционально).

### 2) Основные компоненты
- `db.ts`: схема БД и операции хранения.
- `guidelines.ts`: подбор релевантных версий КР.
- `retrieval.ts`: маршрутизация и объединение retrieval-стратегий.
- `search/providers.ts`: `SqlFtsProvider`, `RuleIndexProvider`, `SourceDocumentProvider`.
- `source-sync.ts`: синхронизация источников и статусы.
- `validation/rule-engine.ts`: основная логика проверки.
- `doctor-llm.ts`, `llm.ts`: врачебное и пациентское объяснение.
- `benchmark.ts`: расчет метрик качества.
- `trials.ts`: поиск clinical trials с кэшем.

### 3) Граница MVP в архитектуре
- В MVP реализованы локальное хранение, retrieval, rules, LLM-надстройка и API.
- Post-MVP: интеграция в клинические ИТ-системы, эксплуатационное масштабирование, расширенный комплаенс.
